# Continuous PW3 monitoring and bounded restart

HealOps runs continuously against the exact `pw3-attendance` container. The base `deploy/compose.monitor.yml` is **observation only**. The additional `deploy/compose.repair.yml` overlay enables deterministic restart after three consecutive failed observations, HTTP Actuator recovery verification, and a maximum of two executed restarts per container per hour. A failed attempt remains failed until healthy and opens a per-incident circuit; a repeated incident within the hour is blocked after the cap. A worker that loses an execution result for two minutes fails the plan closed rather than blindly retrying. PW3 also retains its own `restart: unless-stopped` Docker policy for process exits. HealOps does not itself patch code, merge PRs or deploy application artifacts; PW3's separate production deploy script now has health-gated image/env/Compose rollback.

The worker gets a GET-only Docker socket proxy (`POST=0`) on a private network and cannot mutate containers through its Docker SDK.
During a planned PW3 deployment, the production deploy script creates `maintenance/pw3-attendance` on the host. The worker sees this read-only marker and discards transient Docker Events instead of claiming a restart; after deployment it reconciles the current container. The marker expires after ten minutes to avoid permanent blindness if a runner dies. The dashboard may briefly show a stale monitor while maintenance is active. This prevents HealOps from restarting an application that is still booting during an intentional deployment. A **separate executor** mounts the full Docker socket. The executor accepts only authenticated `/restart` JSON with an exact 64-character container ID and verifies the configured name, Compose project, service and image; it allows at most two restarts per hour. It has no published port and shares a private `action` network only with the worker. This is risk reduction, **not host-level sandboxing**: executor compromise can still control the Docker daemon, and the read-only proxy permits reading other containers' metadata. Production log capture is disabled to avoid copying secrets into HealOps.

For this host, an ignored mode-600 `.env.monitor` contains distinct admin/worker/executor tokens and the registered target/Actuator URL. Never commit or paste it into chat. Start or update the repair stack:

```bash
docker compose -f deploy/compose.monitor.yml -f deploy/compose.repair.yml up -d --build
docker compose -f deploy/compose.monitor.yml -f deploy/compose.repair.yml ps
```

The dashboard is local-only at `http://127.0.0.1:8088`. From another computer use `ssh -L 8088:127.0.0.1:8088 user@server`, then enter the administrator token from `.env.monitor`. The API shows stale/offline if no worker observation arrives for 20 seconds. The worker polls every five seconds and also consumes allowlist-filtered Docker Events. The demo stack in `deploy/compose.auto-demo.yml` runs on separate loopback ports 18088/18099 and was used to verify a real failed endpoint → automatic approval → executor restart → HTTP recovery → audit record without touching PW3.

A full server outage stops the same-host monitor too; external monitoring is required. HTTP health success does not verify mail delivery or every PW3 feature. For source fixes, isolated tests, signed deployment artifacts and rollback must be in place before enabling automatic promotion to production.
