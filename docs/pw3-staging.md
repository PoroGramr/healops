# Isolated PW3 staging and candidate rollout

`deploy/compose.pw3-staging.yml` runs a separate MySQL 8, MinIO and PW3 app on `127.0.0.1:18080` with volumes and networks named `healops-pw3-stage_*`. It **never** joins the production `web` network or uses the production DB, object store, mail, SMS or webhook credentials. The application is reachable only on loopback. Staging uses a locally generated ignored `.env.staging` (mode 600; `deploy/staging.env.example` lists keys), and the registered source directory contains an ignored `app.jar`. Do not use real user data or production secrets.

The live staging instance was verified with PW3 Flyway migrations v1–v6, a synthetic `STAGING_SYNTHETIC` student and test class, a `pw3-stage` MinIO bucket/file round trip, and `GET /actuator/health` returning `UP`. Re-running the stack retains the test volumes. **Only the app** has a second bridge network to expose `18080`; MySQL and MinIO stay on an internal network.

For an untrusted candidate, create a Git worktree from tracked source only (no `.env`, `app.jar` or user files). `patch-runner/pw3-test.Dockerfile` builds a local test image from Playwright Java v1.63 plus JDK 17 and the host's Gradle dependency cache. The test job runs non-root with no network, Docker socket or writable source mount; it copies tracked source to an ephemeral tmpfs, runs offline Gradle tests and `bootJar`, and optionally writes just `/out/app.jar`. The test image must be built locally with a separate `gradlecache` build context; **never copy the host home or production env into the image**.

Build a candidate image from that tested `app.jar` using PW3's Dockerfile and only the artifact directory as Docker build context. Pass its local `sha256:` image ID to `scripts/staging_rollout.py --image ...`. The script checks staging's exact Compose labels and healthy baseline, replaces only the staging image, verifies Actuator `UP` plus `/qr-display.html`, and on failure retags/recreates the previous staging image and verifies recovery. A deliberately bad candidate was deployed and the script returned a nonzero status **after** restoring the previous healthy image. A tested Java candidate was also deployed successfully. The synthetic MySQL row and MinIO fixture survived both.

This is **application image rollback, not database rollback**.
An end-to-end synthetic Java fixture on a separate PW3 clone exercised the optional Codex → allowlisted source diff → networkless Gradle/Playwright tests → JAR export → Docker candidate → staging promotion pipeline. The deliberately failing baseline test became green and staging returned `UP`; no fixture source or PR was pushed to the PW3 production repository. The PW3 `main` workflow now has health-gated image/env/Compose rollback, exercised with offline failure tests; production has not been deliberately broken to test it. Database migrations are not rolled back. A candidate containing Flyway schema/data migrations can irreversibly mutate staging or production, so `stage_pw3=True` rejects migration and deployment file paths. Staging success alone does not authorize unattended PR merging or promotion to the real database.
