# Security model and limits

The dashboard binds to loopback; API and worker use distinct Bearer tokens stored in ignored local env files. Do not publish the dashboard or socket proxy on a public network. No LLM response is executed as shell code.

Profiles:

- `deploy/docker-compose.yml`: **disposable demo only**. The worker directly mounts `/var/run/docker.sock`, which grants effective host control despite the application allowlist.
- `deploy/compose.monitor.yml`: always-on observation. The worker talks to a Docker socket proxy over an internal network with `POST=0`, so Docker writes are denied. It can still read other container metadata through permitted GET calls; this is not per-container read isolation. Production logs are not captured by default.
- `deploy/compose.repair.yml`: optional overlay for PW3. A separate executor on a private network mounts the full socket; it verifies exact container ID, name, image, Compose project/service and a distinct token, with an in-process two-per-hour limit. **Compromising that executor still grants host-level Docker authority.** Worker and API never mount the raw socket. A policy auto-approves restart only after three consecutive faults for the exact configured name; the API also caps executions per hour. Docker Events/polling are hints, not authority to run arbitrary commands. Persistent failure ends in a failed incident; no blind infinite retry.

There is no unattended source patch, real GitHub PR, PR merge, deployment or rollback yet. The experimental [Codex adapter](patch-proposals.md) runs unsandboxed *inside an ephemeral Docker sandbox* because the native host bubblewrap sandbox cannot write. It mounts the existing OAuth file read-only; model-executed code inside the network-enabled container could still read and exfiltrate it. This accepted risk is scoped to opt-in jobs, not the production incident loop. Existing PW3 GitHub Actions deploys from `main` without an automated rollback; do not treat a successful restart test as proof that code deployment is safe. The `Deployment` table is reserved schema, not a working rollback. Administrator approval remains the default for the disposable demo; the PW3 repair overlay explicitly enables policy auto-approval for restart only.

The dashboard token is held in browser sessionStorage, so XSS would expose it. Local HTTP has no TLS; reach it through an SSH tunnel. When log capture is enabled for a disposable demo, 8 KiB of logs may include sensitive information. Do not send production logs to an untrusted LLM. A same-host monitor cannot detect a complete host outage. Remaining requirements before general production use include stronger process isolation for socket operations, per-container authorization at the Docker API boundary, an external watcher, secret redaction, artifact provenance, robust canary/rollback and security review.
